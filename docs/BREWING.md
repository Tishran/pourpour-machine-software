# Конструктор рецептов First Brew: проект и границы точности

Статус: **фаза 8 — все фазы готовы**: справочники, движок, API, форма, таймер, оценка
вкуса, диаграмма TDS/экстракции, исправленный рецепт, свои рецепты и связка с каталогом
и фото. Оценить и исправить можно **любой** кофе, в том числе рецепт обжарщика.
Документ фиксирует контракт
конструктора и места, где нужны калибровка и проверки на
реальных завариваниях. Числа ниже — стартовые настройки, не доказанный оптимум для
конкретного кофе. Версии коэффициентов и справочников должны попадать в результат.

## Место в существующем приложении

- `pourpour.CoffeeService.recipe()` получает неизменённые рецепты обжарщика из живого
  каталога. `recommender.RecipeModel` для неизвестного кофе переносит **целый** рецепт
  из сохранённого датасета; его `closest_reference` и `suggested_baseline` уже помечены
  как предложения, а не проверенные рецепты для новой пачки. Ни этот путь, ни OCR не
  меняем при добавлении конструктора.
- `server.py` обслуживает HTTP, `app.js` хранит интерфейсные строки в `STRINGS.ru/en`,
  экран рецепта и таймер. `brewing_engine.py` не обращается к HTTP, часам,
  случайности или модели. При импорте он однократно загружает валидированные локальные
  JSON-справочники; сами `build` и `rescale` не читают файлы и не меняют входные данные.
  `POST /api/recipes/build` и
  `/api/recipes/adjust` — отдельные пути. Результат помечается `origin: "calculated"`
  и видимым текстом «Собрано по параметрам». Его нельзя обозначать `catalog_match`.
- Рецепт обжарщика в UI: `coffee_g`, `water_g`, `temperature_c`,
  `duration_seconds`, `grind_setting`, `steps[]`; шаги имеют `water_g`,
  `total_water_g`, `start_seconds`, `stop_seconds`, `instruction`.
  Расчётный рецепт использует эту форму как **адаптер для таймера и машины**, но
  хранит собственные `dose_g`, `grind`, `kind`, `why`, `assumptions` и происхождение.
  Никакое преобразование не должно тихо подменять исходный рецепт.

## Вход и справочники

Вход `build(params)` — JSON-совместимый словарь с кодами, а не русскими подписями:
`country`, `processing`, `roast_level` (или Pro-шкала 1–7), `roast_date` **или**
`roast_age_band`, `device_id`, `material`, `filter_id`, `grinder_id`, `dose_g`,
`water_g`. Для Pro допустимы `region`, `variety`, `q_grade`, `water_ph` и
`water_tds_ppm`. Для своей воронки обязательны `device_name`,
`bed_height_mm_at_15g`, `filter_fit`, `material`. Отсутствующее поле остаётся
неизвестным; применённый дефолт перечисляется в `assumptions`. Календарную дату
нужно превращать в возраст на границе API с явной датой расчёта, чтобы чистая
функция не зависела от сегодняшнего дня. OCR даёт лишь предлагаемые значения:
пользователь их подтверждает/правит, а `recognized_fields` хранит происхождение.

Фаза 1 добавила валидируемые JSON-справочники в `webapp/data/`: 40 стран,
13 обработок, 15 устройств, 6 кофемолок, 4 фильтра и 5 материалов. Устройства
содержат тип приготовления, геометрию, класс высоты слоя, посадку фильтра и
число вливаний по умолчанию. Точная высота слоя для готовых моделей оставлена
`null`, поскольку размеры, доза и метод измерения не указаны; для своей воронки
она вводится пользователем. Коды стабильны между языками и версиями. Список
из `recommender.COUNTRIES/PROCESSING` меньше и служит разбору этикетки; расширение
формы не должно менять его правила совпадения. Неизвестные коды — ошибка 400, а
не незаметная замена. Модель/ревизия жерновов, нулевая точка и шкала кофемолки
должны быть частью записи; несовместимые ревизии нельзя объединять по бренду.
`brew_catalog.load_catalog()` проверяет схему, обязательные поля, типы, диапазоны,
уникальность ID и перекрёстные ссылки. Ошибка в данных — `CatalogError`, без
молчаливого исправления и без изменений в живом каталоге обжарщика.

## Выход и структура рецепта

`build` возвращает два упорядоченных варианта с фиксированными `id` (`brighter`,
`sweeter`), одной схемой входа и версией набора правил.
Каждый вариант содержит:

```json
{
  "schema_version": 1,
  "catalog_schema_version": 1,
  "origin": "calculated",
  "engine_version": "2.1",
  "id": "brighter",
  "name": "Ярче",
  "summary": "Стартовый вариант с акцентом на прозрачность",
  "device_id": "v60",
  "method": "percolation",
  "dose_g": 15,
  "coffee_g": 15,
  "water_g": 258,
  "ratio": "1:17.2",
  "temperature_c": 94,
  "grind": {
    "target_particle_microns": 750,
    "setting": "22–23",
    "scale_label": "Comandante C40, клики от нуля",
    "accuracy": "approximate"
  },
  "total_seconds": 170,
  "duration_seconds": 170,
  "steps": [
    {
      "kind": "pour",
      "start_seconds": 0,
      "stop_seconds": 8,
      "pour_g": 38,
      "water_g": 38,
      "total_water_g": 38,
      "instruction": "Предсмачивание",
      "why": "Газ после обжарки может мешать равномерному смачиванию."
    }
  ],
  "reasons": [{"parameter": "temperature_c", "rule": "base_v60", "text": "Стартовая температура для V60."}],
  "context_chips": ["V60", "Светлая обжарка"],
  "assumptions": ["Помол — начальная настройка; подстройте по вкусу и времени слива."]
}
```

Образец **не является готовым полным рецептом**: `steps` здесь укорочены ради
схемы. В реальном варианте сумма `pour_g` точно равна `water_g`, последний
`total_water_g` равен `water_g`, время каждого шага не пересекает следующий,
`duration_seconds` не меньше последнего `stop_seconds`. Везде явно указываются
граммы **влитой** воды; выход напитка — иная величина. Причины возвращаются
структурированно для каждого изменённого параметра/шага, а тексты интерфейса
локализуются в `STRINGS`, не вшиваются только на одном языке в API.

Для иммерсии шаги `fill → steep → drain/press`; для автомата — пустой `steps`
и `automatic_mode: "standard"`, без фиктивных ручных вливаний. Эти шаги совместимы с локальным таймером только
после явного учёта `kind`. Масштабирование `rescale(recipe, dose_g=None,
water_g=None)` создаёт новую копию, сохраняет соотношение, когда изменена одна
из величин, и пропорционально распределяет воду по шагам с остатком в последнем
шаге. При явном изменении обеих величин новое соотношение вычисляется заново.
Тайминги сохраняются как стартовая гипотеза, но не гарантируют такой же слив
при другой высоте слоя.

## Коэффициенты и научная оговорка

Все точные сдвиги живут в одном версионируемом словаре `COEFFICIENTS` в
начале `brewing_engine.py`, с ограничениями по температуре, воде, времени и
помолу. Следующая таблица описывает **реализованные стартовые эвристики для последующей проверки**, а
не найденные в литературе константы. Нейтральная база: V60, 15 г / 250 г
(фактически 1:16,7, не ровно 1:17), вода 93–94 °C, ориентир 2:30–3:00,
предсмачивание и 2–3 последующих вливания. Число вливаний зависит от выбранной
методики и не является требованием производителя. Hario приводит такую дозу и
диапазон температуры в своём [руководстве по V60](https://www.hario.co.uk/blogs/news/how-to-brew-coffee-with-hario-v60-coffee-dripper),
но это не калибровка для каждой партии кофе.

| Признак | Начальное направление | Статус и ограничение |
| --- | --- | --- |
| Светлая → тёмная обжарка | ниже температура, грубее помол, короче контакт | Рабочая эвристика; вкус зависит от экстракции и концентрации, а не от температуры самой по себе. |
| До 14 дней после обжарки | больше воды/времени на смачивание | Основано на дегазации; «14 дней» — условная граница, зависит от обжарки и хранения. |
| Более 2 месяцев | +1 °C и чуть мельче | Потерянную ароматику высокой температурой вернуть нельзя; автоматическая поправка экспериментальна и должна быть проверена по вкусу. |
| Натуральная/анаэробная обработка | пробовать более грубый помол и мягкое вливание | Не доказано, что способ обработки сам по себе всегда даёт больше мелкой фракции; правило требует сравнительного теста. |
| Мытая обработка | пробовать более тонкий помол | Направление условное, не обещать «раскрытия кислотности» в каждом лоте. |
| Плоское дно / высокий слой | менять схему и скорость вливаний, затем помол | Геометрия действительно влияет на напиток, но универсального знака поправки нет. |
| Стекло/металл против пластика | предусмотреть прогрев и возможную температурную поправку | Постоянные «+1–2 °C» без измерения теплопотерь недоказанны. |
| Плотный фильтр | при медленном сливе грубее помол | Фактическое сопротивление зависит от бумаги, посадки и помола. |
| TDS воды / pH | при TDS <75 ppm чуть мельче, при >200 чуть грубее; pH только контекст | TDS не сообщает щёлочность, кальциевую/магниевую жёсткость; эта автоматическая поправка особенно ненадёжна. |

Сдвиги суммируются в фиксированном порядке: обжарка → обработка → возраст →
геометрия/материал/фильтр → TDS воды → метод → цель варианта. Все численные шаги,
включая номинальный помол, промежутки и границы, находятся в `COEFFICIENTS`;
при достижении предела результат ограничивается и остаётся приближённым.
Одно и то же входное значение всегда даёт один результат. Не
нужно представлять оценочный размер помола в микронах как лабораторно измеренную
медиану частиц или прогнозировать точное время слива.
Страна, регион, сорт и Q grade остаются контекстом, пока нет проверенных данных
для количественной поправки; вводить коэффициент только потому, что поле есть
в форме, нельзя. Так же не стоит превращать неназванную «экспериментальную»
обработку в произвольный температурный сдвиг.

### Кофемолки: критическое различие двух «микронов»

**Ход жернова на щелчок ≠ размер частицы.** Для Comandante C40 часто цитируют
около **30 мкм хода на щелчок**, но в доступных [инструкции](https://www.comandantegrinder.com/downloads/c40_manual_EN.pdf)
и [FAQ производителя](https://comandantegrinder.com/pages/faq) точная величина
30 мкм не указана. Производитель даёт для фильтра ориентир **18–35 кликов от
«click zero»** и прямо рекомендует подбирать по вкусу. Поэтому 30 мкм нельзя
помечать как подтверждённую Comandante величину и нельзя использовать формулу
`размер частиц / 30 = клики`. У [1Zpresso K-Ultra](https://1zpresso.coffee/k-ultra/)
официально указан ход жернова 20 мкм/клик — это тоже не размер частиц.

Справочник хранит `burr_travel_microns_per_click` **только с указанием
`micron_kind: "burr_travel"`** и источника; поле `clicks_per_micron` из задания
нельзя применять к `target_particle_microns` без эмпирической кривой конкретной
кофемолки. Чтобы получить числовую настройку из целевого размера частиц, нужна
отдельная проверенная таблица/калибровка `particle_microns ↔ setting`, её версия,
метод измерения распределения и погрешность. Пока её нет, безопасный выход —
стартовый диапазон кликов производителя и подсказка «попробуйте, затем подстройте»
с `accuracy: "approximate"`; неизвестную шкалу не заполнять вымышленным числом.
Для трёх кофемолок тесты проверяют наличие соответствия из пользовательской
таблицы и его приблизительный статус, а не ложную эквивалентность размеров частиц.

Предоставленная Вадимом [таблица соответствия шкал](../Таблица_соотношения_помолов_08_08_1.pdf)
(2 страницы, экспорт Numbers от 13.01.2025) сопоставляет настройки десятков
кофемолок относительно шкалы Mahlkönig EK43 (turkish). В
`webapp/data/grind_equivalences.json` перенесены 13 строк для **Comandante C40
со стандартной осью**, **Baratza Encore** и **1Zpresso K-Plus**. Диапазоны
сохранены как интервалы, без усреднения. Это может помочь перенести знакомую
настройку **между этими конкретными моделями**, но в PDF не описаны метод
измерения, ревизии жерновов, кофе и погрешность. Таблица не содержит прямого
измерения медианного размера частиц в мкм. Числа `400–830` в столбце Mazzer ZM
не следует считать универсальными микронами частиц других кофемолок. Поэтому
эквивалентность помечена `approximate`; движок выбирает ближайшую строку по
**отдельному условному ориентиру** EK43, а номинальный размер частиц не использует
для математического перевода в клики. При отсутствии строки для выбранной модели
`setting: null`. Ориентир EK43 тоже эвристический, не калибровка
`target_particle_microns → setting`. Другой присланный файл —
«Просев кофемолок 2026.pdf» — содержит массы лишь в четырёх широких ситовых
фракциях; он не использован как точный конвертер шкал или размер частиц.

### Реализация фазы 2

`build(params)` принимает коды справочников и возвращает «Ярче» и «Слаще».
Нейтральная база — 15/250 г, 94 °C, 170 с, условная цель 780 мкм и ориентир
EK43 8,5. Варианты сдвигают соотношение на ±0,5, условный помол на ∓30 мкм,
ориентир шкалы на ∓0,5; первый использует меньше вливаний, второй — больше
и на 10 с длиннее контакт. Сдвиги по обжарке, обработке, возрасту, геометрии,
фильтру, материалу и TDS отдельно перечислены в `COEFFICIENTS`, версия `2.0`.
Их причинные объяснения приходят в `reasons` на двух языках. Это **не
измеренные рецепты**: прежде чем рекомендовать их как оптимальные, нужны
сравнительные заваривания и калибровка помола.

Допустимы целые 5–40 г кофе, 80–600 г воды и соотношение 1:12–1:22.
Дата обжарки требует явного `as_of_date` (либо подаётся целый возраст в днях),
поэтому одинаковый вход не зависит от системных часов. Если страна, обработка,
кофемолка или возраст неизвестны, движок не придумывает эти факты; отсутствие
настройки кофемолки даёт `setting: null`. При изменении дозы или воды
`rescale` пересчитывает вливания и сохраняет тайминги как ориентир. Машинная
совместимость отдельно проверяется: только `percolation`, вода ≤400 г; адаптер
дополнительно запрещает расчётные шаги иммерсии и автомата. Тесты фазы 2
проверяют направления сдвигов и инварианты, но не доказывают качество чашки.

### Интерфейс фазы 4

Кнопка на главном экране открывает отдельный мастер: параметры кофе → оборудование
→ два расчётных варианта. Обычный и Pro-режимы используют те же коды справочников;
страны и кофемолки доступны через поля поиска с подсказками, устройства сгруппированы.
Возраст обжарки задаётся пресетом либо датой с явной локальной датой расчёта.
У своей воронки используются название, высота слоя, прилегание фильтра и материал.
Для плотной и слабой посадки добавлена *условная* поправка на сопротивление слива,
также вынесенная в `COEFFICIENTS`; это не измеренная зависимость.

Экран показывает происхождение `calculated`, варианты, причины, время и вес каждого
шага, условный помол и оговорку о настройке кофемолки. Кнопки ± пересчитывают
варианты через `POST /api/recipes/rescale`, избранное хранит только ключи рецептов
в `localStorage`. На мобильном шаги последовательные, на десктопе форма и результат
соседствуют, изменения формы обновляют результат. Рецепт обжарщика, OCR и старый
поиск не изменены. Быстрый режим фото с предзаполнением конструктора — фаза 8.
Таймер строит отдельную шкалу из шагов расчётного рецепта: промежутки между
вливаниями становятся фазами ожидания, после последнего вливания показывается
слив. Для иммерсии выводятся залив, настаивание и слив/отжим; для автомата —
ожидание работы кофеварки без выдуманных вливаний. В начале отдельный экран
готовности, во время заваривания — текущий/общий счётчик, вес на весах,
рекомендованная скорость струи, прогресс шага и ручной переход между шагами.
Пауза сохраняет прошедшее время, активное время считается по `Date.now()`;
Wake Lock, вибрация и звук используются только при поддержке браузером.
Оценка результата и «квадрат» TDS/экстракции — фаза 6.

## После заваривания: измерение и обратная связь

С рефрактометром: `extraction_percent = beverage_g × beverage_tds_percent /
dose_g`. Например, 210 г напитка × 1,35% / 15 г = 18,9%. Здесь `beverage_g`
— **выход напитка**, не 250 г входящей воды. Измерение зависит от калибровки
прибора, температуры и подготовки пробы. [SCA](https://sca.coffee/s/2017-SCA-CHB-Program-Requirements-ba6g.pdf)
использует в сертификации кофеварок ориентиры 1,15–1,45% TDS и 18–22%
экстракции; это не обязательная зона «вкусно» для всех людей. Современное
[обсуждение SCA](https://sca.coffee/sca-news/25/issue-13/towards-a-new-brewing-chart-xpj8t)
предостерегает от жёсткой вкусовой трактовки границ классической диаграммы.
Поэтому SVG показывает измеренную точку и ориентир, но не ставит медицински
точный «диагноз» по пересечению линии. Без рефрактометра — только качественная
оценка вкуса, **без выдуманных TDS/экстракции и точной точки на осях**; допустима
область неопределённости с явной подписью.

`adjust(recipe, feedback)` возвращает новый рецепт, диагноз, изменённые поля,
старые/новые значения и причины. В фазе 3 реализован консервативный набор
правил: кислый/резкий/пустой вкус или измеренная экстракция <18% предлагают
чуть более тонкий помол и +2 °C; горечь/сухость либо экстракция >22% — обратное
направление. «Водянисто» без подтверждённой сладости не сужает соотношение.
Только `sweet + watery` сужает его на 0,5, а `sweet + syrupy` расширяет.
Это стартовые эвристики, а не диагноз по одной чашке: сладость и баланс нельзя
вычислить из TDS. При вкусовой оценке `extraction_percent: null`; при измерении
вычисляется из веса готового напитка, TDS напитка и дозы.
За один цикл меняются не более двух
параметров. Конфликтующие дескрипторы либо исключаются в UI, либо отклоняются
API. Если есть признаки недо-/переэкстракции, сначала меняем экстракционный
рычаг (например, помол или температуру), и **только затем** концентрацию;
«водянисто» не означает автоматически «добавить кофе». Это направление
поддерживается [исследованием вкуса и TDS/экстракции от UC Davis / SCA](https://sca.coffee/sca-news/25/issue-15/manipulating-and-measuring-a-key-attribute-in-drip-brew-coffee-zwlhz),
но конкретный шаг корректировки остаётся эвристикой. Сохранённый пользовательский
рецепт не изменяет исходник обжарщика или датасет.

### Реализация фазы 6

**Дескрипторы.** `taste_options()` отдаёт через `GET /api/catalog/options` (`tastes`)
три колонки формы — «Кислотность и сладость», «Тело и крепость», «Финиш и чистота»
(14 дескрипторов), лимит 3 и попарные конфликты. Конфликт считается одной функцией
для формы и для API: «сбалансированно» исключает всё остальное; признаки
недоэкстракции (кисло, резко, плоско, пусто) — признаки переэкстракции (горько, сухо,
терпко, неясно, грубо, тяжело) и «сладко»; «водянисто» — «сиропно» и «тяжело».
Тест перебирает все пары и проверяет, что форма отключает ровно то, что отклоняет
движок. Названия и пояснения вкусов — строки интерфейса в `STRINGS`.

**Диагноз.** Ответ `adjust` содержит `diagnosis_code`: `under`, `over`,
`weak_after_sweet`, `heavy_after_sweet`, `on_target` или `strength_needs_sweetness`.
Порядок правил: сначала экстракция (температура ±2 °C и условный помол ∓30 мкм — не
больше двух параметров), затем концентрация (вода ±0,5 соотношения), и только когда
отмечена сладость. Крепость без сладости («водянисто» или «сиропно» отдельно) рецепт
не меняет и просит сначала оценить сладость. Измерение с экстракцией 18–22 %, но TDS
вне 1,15–1,45 %, по тому же правилу тоже не меняет воду: рефрактометр не видит
сладости, объяснение предлагает отметить вкус. Если параметр упёрся в границу,
`at_limit: true` и интерфейс так и пишет. Каждое изменение несёт `why`/`why_en`,
для помола — старую и новую настройку шкалы, для воды — старое и новое соотношение.
Исправленный рецепт получает `revision` (1, 2, …) и текущую `engine_version`; если
ничего не изменилось, рецепт возвращается без нового номера. Версия правил — `2.1`;
выход `build` не изменился, поэтому `validate_calculated_recipe` принимает и `2.0`
(`compatible_versions`).

**Диаграмма.** `extraction_chart(recipe, cup)` возвращает геометрию, интерфейс рисует
её инлайн-SVG без библиотек. Оси: экстракция 14–26 %, крепость 0,9–1,8 % TDS; зона
баланса — ориентир SCA 18–22 % и 1,15–1,45 %. Диагонали соотношений 1:12–1:22 и линия
самого рецепта считаются как `TDS = экстракция × доза / (вода − 2 × доза)`:
**2 г воды на грамм кофе, удерживаемые гущей, — приближение**, реальная величина
зависит от метода и помола. По рефрактометру ставится точка
(`выход × TDS / доза`), за пределами осей она прижимается к краю с пометкой. По вкусу
точки нет: рисуется полоса на линии соотношения заваренного рецепта в диапазоне
экстракции, который соответствует диагнозу (`under` 14–18 %, `over` 22–26 %, баланс
18–22 %, «сначала сладость» — вся ось). `extraction_percent` и `tds_percent` при
вкусовой оценке остаются `null`. Все эти числа лежат в `COEFFICIENTS['chart']`.

**Интерфейс.** Мастер теперь из пяти шагов: «О кофе → Оборудование → Стартовые
рецепты → Результат → Правка», в шапке — «назад» и «закрыть». На шаге рецептов рядом
с «Заварить» стоит «Оценить вкус»; после таймера расчётного рецепта (и после машины)
главная кнопка — тоже «Оценить вкус», и оценка начинается заново для новой чашки.
Шаг «Результат»: карточка оцениваемого рецепта, переключатель «По вкусу /
Рефрактометр», три группы чекбоксов с подсказкой «?» у каждого (toggletip с
`aria-expanded`) и автоматическим отключением противоречий; для рефрактометра — TDS,
выход, доза (должна совпадать с рецептом) и время слива, предпросмотр экстракции
и понятные ошибки. Шаг «Правка»: вид правки, диагноз одной фразой, объяснение,
диаграмма с легендой и оговоркой, список «что меняем» и исправленный рецепт с
кнопками ± для дозы, воды (через `/api/recipes/rescale`) и температуры (80–99 °C).
Внизу — «Заварить исправленный» и «Сохранить как свой». На десктопе оценка слева,
правка справа и обновляется при изменении вкуса. Оценку можно повторять: исправленный
рецепт заваривается, оценивается и даёт «правку 2».

**Сохранение.** «Сохранить как свой» пишет в `localStorage` ключ
`firstbrew.myRecipes.v1` — массив до 50 самодостаточных записей
`{format: "firstbrew.recipe", version: 1, id, key, saved_at, recipe, context_chips,
feedback, diagnosis_code, measurement_kind, extraction_percent}`. `recipe` — объект
движка без переводов, поэтому запись можно перенести на сервер без переделки. Список,
повтор, удаление и экспорт — фаза 7.

### Реализация фазы 7: свои рецепты

**Хранение.** Все сохранённые расчётные рецепты — один список в `localStorage`,
ключ `firstbrew.myRecipes.v1`, до 50 записей, новые сверху, без регистрации и без
базы на сервере. Запись:

```json
{
  "format": "firstbrew.recipe", "version": 1,
  "id": "own-mfx3k2-8d1q0a", "key": "[\"v60\",\"brighter\",1,15,258,97,700,\"20–21\"]",
  "saved_at": "2026-09-23T09:12:00.000Z",
  "source": "corrected",
  "title": "Утренний V60",
  "context_chips": ["Эфиопия", "Мытая", "Hario V60", "Светлая"],
  "brew_count": 1, "last_brewed_at": "2026-09-23T09:20:00.000Z",
  "feedback": {"descriptors": ["sour"]}, "diagnosis_code": "under",
  "measurement_kind": "taste_only", "extraction_percent": null,
  "recipe": {"origin": "calculated", "engine_version": "2.1", "revision": 1, "…": "объект движка"}
}
```

`source` — `built` (стартовый вариант), `corrected` (после правки) или `shared`
(по ссылке). `recipe` — неизменённый объект движка без переводов, поэтому запись
переносится на сервер как есть: для аккаунтов достаточно хранить этот JSON и
проверять `recipe` той же `restore_recipe`. `key` не даёт сохранить один рецепт
дважды. `context_chips` — подписи на языке сохранения, только для показа. Записи
при чтении проверяются по форме; повреждённые пропускаются. Кнопка на шаге рецептов
теперь называется «Сохранить в мои рецепты» и пишет в тот же список; старый ключ
`firstbrew.favorites.v1` хранил только отпечатки без рецептов, восстановить из него
нечего, поэтому он больше не читается.

**Экраны.** На главном экране кнопка «Мои рецепты · N» (только если N > 0) ведёт
к списку: название, числа, контекст, происхождение и дата. Карточка рецепта:
происхождение, чем была вызвана правка, своё название, плитки без правки на месте,
шаги, причины, отправка на машину для совместимой воронки, экспорт и удаление с
подтверждением. Внизу «Заварить» и «Оценить вкус»: таймер возвращается к карточке,
счётчик заварок растёт, оценка ведёт на шаги «Результат/Правка» мастера, а «назад»
оттуда — снова к карточке. Исправление сохраняется новой записью; исходная остаётся.

**Экспорт.** «Скопировать текст» даёт читаемый рецепт: название, пометку «не рецепт
обжарщика», контекст, дозу, воду, соотношение, температуру, помол с условной целью,
время, шаги «старт · на весах · действие», оговорку о стартовых настройках и ссылку.
«Скопировать ссылку» и системное «Поделиться…» (где оно есть) дают адрес вида
`…/app#recipe=z<base64url>`. Рецепт лежит во фрагменте адреса, который браузер не
отправляет на сервер; сервер ничего не хранит. В ссылку идёт объект движка **без**
`reasons`, `assumptions`, подписей и названий вариантов, плюс своё название и
контекст; JSON сжимается `CompressionStream('deflate-raw')` (префикс `z`, около 1 КБ
для исправленной воронки) или, если браузер не умеет сжимать, передаётся как есть
(префикс `j`, около 2,5 КБ). Обе длины помещаются в сообщение мессенджера.

**Импорт.** При открытии такой ссылки (или вставке её во вкладку с приложением)
фрагмент сразу убирается из адреса, распаковывается с лимитом 60 КБ и отправляется
в `POST /api/recipes/import` с телом `{"recipe": …}`. `restore_recipe` проверяет
рецепт как `validate_calculated_recipe`, требует, чтобы тексты шагов были из набора
движка (`_STEP_TEXTS`), пересчитывает настройку помола по таблице и совместимость с
машиной, отбрасывает все неизвестные поля и вместо объяснений добавляет одну честную
причину: «объяснения исходных поправок не передаются». Название и контекст из ссылки
только показываются (строки, обрезка до 80/60 символов, экранирование). Рецепт по
ссылке сначала открывается как «Получено по ссылке, пока не сохранён» с кнопками
«Сохранить себе» и «Заварить»; повреждённая ссылка ведёт на список с понятной ошибкой.

### Реализация фазы 8: любой кофе

**Рецепт обжарщика тоже оценивается.** `adopt_roaster_recipe(recipe, source)` и
`POST /api/recipes/adopt` с телом `{"recipe": <рецепт обжарщика>, "source": {"name",
"url", "kind"}}` переводят рецепт обжарщика в формат движка **без изменения чисел**:
доза, вода, температура, время, шаги с их текстами, кофемолка и настройка остаются как
опубликованы. Копия помечена `basis: "roaster"`, `id: "roaster"` и `source` (название
кофе, страница `theweldercatherine.ru/catalog/…` либо `null`, вид: каталог,
`catalog_match`, `closest_reference`, `suggested_baseline`). Неполный или
противоречивый рецепт (нет дозы, времени или объёма вливаний, вливания пересекаются,
сумма не сходится с водой) отклоняется с ошибкой 400 и понятным сообщением в интерфейсе —
ничего не дописывается. Из 37 рецептов датасета так принимаются 35; два неполных
отклоняются, те же, что рекомендатель помечает непригодными. Сам рецепт обжарщика,
его загрузка, OCR и рекомендатель не менялись.

Правка идёт по тем же правилам (не больше двух параметров, крепость только после
сладости), но **помол двигается от настройки обжарщика**: `grind.source_setting`
хранит её, `steps_from_source` — на сколько шагов ушли (не больше ±6). Шаг —
пол-деления для EK43 (в датасете все рецепты на Mahlkönig EK43 ICON, 11–13) и одно
деление/клик для остальных; меньшее число считается более тонким помолом, как на EK43,
Comandante и 1Zpresso — это допущение записано в `COEFFICIENTS['roaster']`. Если
настройка не число, правка остаётся относительной («на 1 шаг мельче»). Исправленная
копия получает `revision` и подпись «Исправлено по вашей оценке · на основе рецепта
обжарщика, уже не его рецепт»; неизменённая — «Рецепт обжарщика без изменений».
Такая копия работает везде: таймер, машина, «Мои рецепты», ссылки (`restore_recipe`
проверяет источник, тексты шагов как простой текст до 80 символов без управляющих
символов и пересчитывает настройку помола).

**Предзаполнение конструктора.** Поля заполняются тем, что действительно известно:
сначала подтверждённые на фото признаки (страна, обработка, сорт, регион, тёмная
обжарка по слову «эспрессо»), затем профиль кофе из сохранённого датасета —
`GET /api/coffee/profile?url=<страница кофе>` отдаёт страну, обработку, сорт и регион
для 37 из 40 кофе каталога. Для остальных страна берётся из начала названия. Коды
распознавания совпадают с кодами справочника стран (ISO); обработки переводятся так:
мытая, натуральная, хани, «анаэробная + мытая/натуральная» → соответствующая
анаэробная. Остальное (дата и степень обжарки, оборудование) человек заполняет сам.
Заполненные поля помечены «Распознано по фото» или «Из каталога обжарщика»; метка
исчезает, когда поле поправили.

**Пути.** Фото → подтверждение: если кофе найден в каталоге, первым идёт рецепт
обжарщика, вторым — «Собрать по параметрам»; если не найден — главная кнопка
«Собрать рецепт для этого кофе» (конструктор с распознанным), запасная — похожий рецепт
обжарщика; нечитаемое фото — «Заполнить параметры вручную». На экране рецепта
обжарщика рядом с «Начать заваривание» стоит «Оценить вкус», ниже — блок «Собрать по
параметрам»; после таймера рецепта обжарщика главная кнопка — «Оценить вкус». «Назад»
с оценки возвращает к рецепту обжарщика.

**Быстрый режим.** На первом шаге мастера есть «Заполнить по фото пачки» (только если
распознавание доступно на сервере). Снимок уходит в тот же `POST /api/label`, что и
на главном экране, распознанные поля подставляются с пометкой, уже выбранное
оборудование сохраняется, а если кофе найден в каталоге, над формой появляется
«…есть в каталоге обжарщика — сначала стоит попробовать его рецепт» с кнопкой
«Открыть рецепт обжарщика». Фото, как и раньше, не сохраняется. По просьбе заказчика
отсутствующие поля (дата и степень обжарки, воронка, кофемолка) спрашиваются, поэтому
режим не пропускает форму полностью, а заполняет её.

**Поля «Страна» и «Кофемолка»** — комбобокс вместо `datalist`, который браузеры
показывали только при наборе: список открывается по касанию, фокусу или стрелке,
отсортирован по алфавиту текущего языка, фильтруется по русскому и английскому
названию, управляется стрелками, Enter и Esc (`role="combobox"`, `aria-expanded`,
`aria-activedescendant`).

## Совместимость с First Brew machine

По [протоколу](PROTOCOL.md) и `machine.recipe_to_machine` машина принимает
`coffee_g`, `water_g`, `temperature_c`, `duration_seconds` и **только список
управляемых вливаний** с `total_water_g`, `start_seconds`, `stop_seconds`.
Лимиты текущего симулятора/прошивки: температура 40–99 °C, вода ≤400 г,
длительность ≤600 с, 1–12 вливаний; времена не перекрываются, цели не убывают.
Для `percolation` движок формирует совместимые поля; `recipe_to_machine` проходит
для вариантов в пределах лимитов. Шаги ожидания не отправляются: паузы
получаются промежутками между вливаниями. `immersion`, `hybrid` и
`automatic_drip` **не отправлять как обычную схему помпы**, пока аппаратная
поддержка этого режима не определена. Это лучше, чем показывать ложную кнопку
«Заварить на машине». Кнопка у расчётной воронки появляется только при
подключённой машине и `machine_compatible: true`. Интерфейс отправляет
исходный расчётный объект в `POST /api/machine/recipe`, а серверный адаптер
преобразует совместимые поля в `load_recipe`; браузерный сценарий проверяет
отправку, unit-тест — допустимый пакет протокола. Рецепт обжарщика
передаётся как сейчас, без правок.

## Порядок реализации и критерии проверки

1. Фаза 1: справочники с источником, точностью, типом микронов и валидацией — готово.
2. Фаза 2: чистые функции, версия коэффициентов, независимый метод для
   иммерсии/автомата, `rescale`, тесты направлений и инвариантов — готово.
3. Фаза 3: API и ошибки входа; никакого доступа движка к живому каталогу — готово.
4. Фаза 4: мобильная форма, два языка, варианты, пересчёт — готово.
5. Фаза 5: таймер для воронки, иммерсии и автомата, проверка отправки

После фазы 8 проходят все четыре браузерных сценария: `browser-smoke`, `browser-machine`

обновлены под русский язык по умолчанию и новые экраны.

На каждой фазе — `cd webapp` и `python3 -m unittest discover -s tests -v`
(из корня эквивалентно `PYTHONPATH=webapp python3 -m unittest discover -s
webapp/tests -v`), отдельный коммит и остановка для просмотра. Сквозной
Playwright-сценарий, 375×812,
клавиатура и доступные имена нужны, когда соответствующий путь появится:
после одной только документации невозможно пройти «форма → таймер → вкус».

разных кофе и оборудовании; внутренняя самосогласованность тестов не
доказывает вкусовое качество.
