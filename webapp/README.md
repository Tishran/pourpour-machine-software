# First Brew

Web app: название или фото пачки → этикетка кофе → рецепт воронки.

Распознавание фото и подбор рецепта для нового кофе описаны в [ML README](../ml/README.md).
Фото обрабатывается локально (Tesseract + Pillow), после распознавания удаляется.
Для известного кофе показываем исходный рецепт; для нового — явно отмеченное предложение
на основе похожего лота из датасета. Достаточно даже одной страны, например
«Колумбия»: при отсутствии обработки берём исходный рецепт, близкий к типичным
параметрам лотов этой страны. После любого фото, включая точное совпадение,
показывается подтверждение распознанных признаков. Нечитаемый снимок не открывает
рецепт: общий стартовый вариант доступен только по отдельному нажатию.
Неизвестные характеристики не додумываем.

## Конструктор рецептов (фазы 1–8)

Подготовлены справочники для отдельного расчётного конструктора: 40 стран,
13 обработок, 15 устройств, 6 кофемолок, 4 фильтра и 5 материалов в `data/*.json`.
`brew_catalog.load_catalog()` проверяет схемы, диапазоны, уникальность кодов и
ссылки между файлами; ошибки данных не скрываются. Запуск проверки:

```sh
cd webapp
python3 -m unittest tests.test_brew_catalog -v
```

Отдельная таблица `data/grind_equivalences.json` содержит ориентировочные
соответствия шкал трёх кофемолок из присланного PDF. Это не перевод настройки
в размер частицы: шаг жернова и ситовые фракции — разные величины. Методология,
ограничения и план движка описаны в [docs/BREWING.md](../docs/BREWING.md).
`brewing_engine.build(params)` теперь выдаёт два расчётных варианта — «Ярче» и
«Слаще» — и объяснения поправок. `rescale(recipe, dose_g=None, water_g=None)`
пересчитывает воду и вливания без изменения исходного рецепта. Для иммерсии
шаги «залив → настаивание → слив/отжим», для автомата ручных вливаний нет.
Помол и все настройки приблизительные; таблица соответствий не переводит
микроны частиц в клики. Проверка движка:

```sh
cd webapp
python3 -m unittest tests.test_brewing_engine -v
```

API доступен до появления новой формы:

- `GET /api/catalog/options` — проверенные справочники и таблица соответствий помола.
- `POST /api/recipes/build` — тело `{"params":{"device_id":"v60","roast_level":"light"}}`, ответ `{"variants":[…]}`.
- `POST /api/recipes/adjust` — тело `{"recipe":<вариант из build>,"feedback":{"descriptors":["sour"]}}`
  либо `feedback.measurement` с `beverage_tds_percent`, `beverage_g`, `dose_g`,
  `drawdown_seconds`. Ответ содержит `recipe` (с номером `revision`), `diagnosis`,
  `diagnosis_code`, `explanation`, `changes`, геометрию диаграммы `chart` и, только
  при измерении, `extraction_percent`/`tds_percent`. `GET /api/catalog/options`
  дополнительно отдаёт `tastes`: колонки дескрипторов, лимит и конфликты.
- `POST /api/recipes/import` — тело `{"recipe":<рецепт из ссылки>}`; ответ `{"recipe":…}`
  собран заново только из проверенных полей (помол по таблице, тексты шагов из набора
  движка, без посторонних полей). Используется при открытии ссылки на рецепт.
- `POST /api/recipes/adopt` — тело `{"recipe":<рецепт обжарщика>,"source":{"name":…,"url":…,"kind":…}}`;
  ответ — неизменённая копия рецепта обжарщика в формате движка для оценки и правки.
  Неполный рецепт — 400.
- `GET /api/coffee/profile?url=<страница кофе>` — страна, обработка, сорт и регион кофе
  каталога из сохранённого датасета (или `null`) для предзаполнения конструктора.
- `POST /api/recipes/rescale` — тело `{"recipe":<вариант>,"dose_g":20,"water_g":null}`;
  пересчитанный рецепт возвращается в поле `recipe`.

Для POST нужен `Content-Type: application/json`; ошибка входа даёт 400, слишком
большое тело — 413, неверный формат — 415, чужой Origin — 403. Правка пока
консервативная и меняет не больше двух параметров. С главного экрана теперь
открывается мобильный мастер: «О кофе → Оборудование → Стартовые рецепты».
Есть обычный и Pro-режимы, подсказки к полям, своя воронка, два варианта,
объяснения параметров, кнопки пересчёта дозы/воды и избранное на устройстве.
На десктопе форма и результат стоят рядом; RU/EN работают в обоих размерах.

Расчётный рецепт открывает экран готовности с дозой, водой, температурой, помолом
и общим временем. Таймер ведёт по вливаниям и паузам: показывает текущий шаг,
накопительный вес на весах, скорость струи, остаток и следующий шаг. Есть
пауза, переход назад/вперёд, звук, вибрация и удержание экрана включённым,
если браузер поддерживает Wake Lock. Время считается от системных часов, поэтому
сворачивание вкладки не задерживает рецепт. Для иммерсии таймер показывает
залив, настаивание и слив/отжим; для автомата — время работы без фиктивных вливаний.
Совместимый рецепт воронки можно отправить на подключённую машину First Brew;
иммерсия и автомат в помповый протокол не отправляются.

После заваривания расчётного рецепта (или кнопкой «Оценить вкус» рядом с «Заварить»)
мастер переходит к шагам «Результат» и «Правка». Вкус отмечается 1–3 дескрипторами
из трёх групп, у каждого есть подсказка «?», противоречащие варианты гаснут сами.
С рефрактометром вводятся TDS, выход напитка, доза и время слива. Движок ставит
диагноз одной фразой, объясняет его, меняет не больше двух параметров и не делает
чашку крепче, пока не отмечена сладость. Диаграмма экстракции (инлайн-SVG) показывает
зону баланса SCA, диагонали 1:12–1:22, линию рецепта и точку измерения либо полосу-оценку
по вкусу. Исправленный рецепт можно поправить кнопками ±, заварить (в том числе на
машине) и сохранить на устройстве.

«Мои рецепты» (фаза 7): стартовые варианты и исправленные рецепты сохраняются
в `localStorage` (`firstbrew.myRecipes.v1`, до 50 записей, без регистрации). На
главном экране появляется кнопка «Мои рецепты · N» со списком; в карточке рецепта
можно заварить его ещё раз (в том числе на машине), оценить вкус и получить новую
правку, дать своё название, скопировать рецепт текстом или ссылкой, поделиться и
удалить с подтверждением. Ссылка несёт рецепт во фрагменте адреса (сервер его не
хранит), при открытии рецепт проверяется сервером и предлагается «Сохранить себе».
Любой кофе (фаза 8): у рецепта обжарщика есть «Оценить вкус» — правка делается
по его неизменённой копии, помол двигается от настройки обжарщика, а результат
подписан как исправление на основе рецепта обжарщика. Рядом предлагается «Собрать по
параметрам» с полями из каталога. Если кофе с фото не найден в каталоге, главная кнопка
ведёт в конструктор с распознанными полями (пометка «Распознано по фото»), остальное
заполняется вручную. В самом конструкторе есть быстрый режим «Заполнить по фото
пачки»: поля подставляются из снимка, выбранное оборудование сохраняется, а кофе из
каталога предлагается сначала с рецептом обжарщика. Страна и кофемолка выбираются из
выпадающего списка с поиском.
Алгоритмы каталога, OCR и рекомендателя не менялись. Подробности — в [docs/BREWING.md](../docs/BREWING.md#реализация-фазы-7-свои-рецепты).
Проверка интерфейса:

```sh
cd webapp && .venv/bin/python server.py --port 8013 --machine sim --sim-speed 20
for test in browser-smoke browser-machine browser-mobile browser-constructor browser-membership; do
  POURPOUR_TEST_URL=http://127.0.0.1:8013 node ../ml/tests/$test.cjs
done
```

Старые сценарии стартуют как демо-подписчик с машиной и режимом «Просто рецепт сейчас»
(`ml/tests/demo-state.cjs`): они проверяют рецепты, а не развилку и лимиты.

## Подписка, Школа, рецепты чемпионов

Приложение ведёт себя так, как сказано в питче: **One membership. Three ways in.**
Настоящих платежей, карт и аккаунтов нет — тариф хранится на устройстве, везде видно
«Демо: оплата не подключена». Подробная карта прав и статус фаз — в
[docs/MEMBERSHIP.md](../docs/MEMBERSHIP.md).

- **Тарифы** — `data/plans.json` (три тарифа, цены-заглушки, права, лимиты, фразы
  пользы для замка). Проверяется `plans.py` при старте сервера, отдаётся `GET /api/plans`.
  Цены, лимиты и тексты карт меняются только в этом файле.
- **Права в браузере** — один модуль `entitlement()`, `can(feature)`, `limit(name)`,
  `used(name)`, хранение `firstbrew.membership.v1`. Закрытая функция видна с 🔒 и одной
  фразой пользы; шторка закрывается одним нажатием, не появляется во время заваривания и
  показывается не чаще раза за визит на одном экране. **Машина — право владельца**
  (`machine_brew`), а не платного тарифа: на плане `free` владелец отправляет на машину
  рецепт обжарщика и любой сохранённый рецепт.
- **Развилка первого запуска**: «Научи меня» / «У меня машина First Brew» / «Просто рецепт
  сейчас». Главный экран зависит от режима; ссылка на рецепт открывает рецепт сразу.
  Экран настроек: язык, звук, вибрация, режим, тариф и демо-переключатели (тариф,
  владелец машины, сброс лимитов, конец включённых месяцев).
- **Learn why** — у каждого числа рецепта «Почему?»; в таймере строка «зачем этот шаг»;
  после правки — «Что вы узнали». Тексты — `data/course.json` (поле `source` у каждого),
  `GET /api/course`.
- **Школа** — 6 модулей, 14 уроков-черновиков в `data/course.json`: карточки теории →
  практика (рецепт из движка, таймер или машина) → оценка и правка → вывод. Эксперименты
  используют `POST /api/recipes/experiment` (`brewing_engine.experiment_pair`): тот же рецепт
  дважды, во второй чашке ровно один параметр на шаг. Прогресс — `firstbrew.school.v1`.
- **Дневник и прогресс** — `firstbrew.journal.v1` (до 200 записей, ссылка на рецепт, а не
  копия), доля отличных чашек по диагнозу движка, серия дней, уроки, ваш вкус.
- **Рецепты чемпионов** — `data/champion_recipes.json`, проверка `champions.py`,
  `GET /api/champions`. Файл пуст: на главном экране честное «Скоро: рецепты чемпионов».

### Как добавить рецепт чемпиона

Запись в `items` файла `webapp/data/champion_recipes.json` (пример —
`webapp/tests/fixtures/champion_recipes.json`):

```json
{
  "id": "surname_2026", "barista": "Имя Фамилия", "event": "Название чемпионата",
  "year": 2026, "place": 1, "brewer": "Hario V60",
  "coffee": {"country": "Эфиопия", "processing": "washed", "variety": null},
  "coffee_g": 15, "water_g": 250, "temperature_c": 93, "duration_seconds": 180,
  "grind_setting": null, "grind_description": "средне-мелкий",
  "steps": [{"instruction": "Предсмачивание", "water_g": 50, "start_seconds": 0, "stop_seconds": 10}],
  "source_url": "https://…", "source_note": "Где и когда опубликован рецепт"
}
```

Все поля обязательны (неизвестное — `null`, но нужен `grind_setting` или
`grind_description`). Вливания должны в сумме давать `water_g`, времена не
пересекаются; неполная запись — ошибка при старте сервера, а не тихий пропуск.
Данные не скачиваются и не придумываются: только опубликованные рецепты с источником.

## Запуск

Для поиска в живом каталоге нужен Python 3.11+ и доступ в интернет; внешних библиотек не требуется.
Для фото нужны Tesseract, Pillow и языковые веса: [инструкция установки](../ml/README.md#install-and-run).
API-ключи не нужны. Подбор по сохранённой базе и распознавание фото после установки работают без сети.

```sh
python3 server.py
```

Открыть http://127.0.0.1:8000. Для другого порта: `python3 server.py --port 8080`.

## Возможности

- Поиск по названию, его части и транслитерации; похожие названия при опечатке отмечаются отдельно.
- Только лоты с обжаркой под фильтр из текущей выгрузки. Фасовки одного лота объединяются.
- Только рецепты `DRIPPER`; эспрессо, аэропресс и батч-брю исключаются.
- Доза, вода, температура, общее время, исходная настройка кофемолки, шаги и накопительный вес воды на весах.
- Переключение вариантов рецепта, если источник вернул несколько.
- Таймер с паузой, сбросом и подсветкой текущего вливания. Самостоятельно не управляет кофемашиной.
- Ссылки на карточку кофе и исходные данные, время загрузки и отметка устаревшего кэша.
- Мобильный интерфейс из трёх экранов (см. ниже), управление с клавиатуры, отдельные состояния ошибок и отсутствующего рецепта.

## Мобильный интерфейс

Приложение сделано как простое мобильное приложение: телефон в одной руке, чайник в другой.
По умолчанию интерфейс открывается на русском языке.
Переключатель RU/EN всегда виден в шапке первого экрана; выбор вместе со звуком и вибрацией
хранится в `firstbrew.settings.v1`. Все строки — в `STRINGS.en` и `STRINGS.ru` в `static/app.js`. Формулировки описательные,
не повелительные («Pouring to 150 g», «Waiting», «Water draining»): во время заваривания
приложение показывает, что происходит, а не командует.

Основные экраны и отдельный шаг подтверждения фото: переходы без перезагрузки,
кнопка «назад» браузера работает (History API):

1. **Find.** Главная кнопка «Сфотографировать пачку» открывает камеру
   (`accept="image/*" capture="environment"`), второстепенная «Выбрать из галереи» —
   отдельный input без `capture`. На десктопе одна кнопка «Choose a photo». Ниже поиск.
   Список кофе появляется после ввода (с задержкой 300 мс) или по кнопке «Show all».
   Статусы («Loading the catalog…», «Reading the label…») показываются одной строкой над кнопкой.
2. **Recipe.** Название, четыре крупные цифры (кофе, вода, температура, время), помол,
   соотношение, список вливаний: время начала, что происходит, сколько долить и целевой вес
   на весах. Внизу закреплена кнопка «Start brewing» (учитывает `safe-area-inset-bottom`).
   Если рецептов несколько, переключатель вариантов наверху. Известные оговорки API
   локализуются, исходные параметры рецепта и неизвестные заметки источника сохраняются.
   Маленькое фото и ссылка «Что распознано» раскрывают подтверждённые признаки.
3. **Brewing.** Полноэкранный таймер: текущее время, фаза («Bloom · 1 of 5», «Waiting»,
   «Drawdown»), текущее действие («Pouring to 150 g»), обратный отсчёт до следующего вливания,
   полоса общего прогресса, следующий шаг мелко внизу. Кнопки «Pause»/«Resume» и «Reset».
   По окончании экран «Done» с кнопками «Brew again» и «Find another coffee».

Жесты и клавиатура: всё управляется тапом, ничего не зависит от hover; кликабельные элементы
не меньше 48×48 px; фокус видимый; поиск запускается по Enter (`enterkeyhint="search"`).

Во время заваривания:

- экран не гаснет (`navigator.wakeLock`; если API недоступен, ничего не ломается, но экран
  может погаснуть по настройкам телефона);
- в начале каждого вливания короткая вибрация (`navigator.vibrate`) и негромкий звук
  (Web Audio). Оба отключаются кнопками наверху экрана, настройка запоминается в `localStorage`.

Тёмная тема включается по `prefers-color-scheme` через те же CSS-переменные;
`prefers-reduced-motion` отключает анимацию. На ширине от 900 px экраны «Find» и «Recipe»
показываются рядом, таймер остаётся полноэкранным.

Приложение добавляется на главный экран телефона: `manifest.webmanifest` (`display: standalone`),
иконки 192/512 px и `apple-touch-icon`. Service worker не используется, офлайн-режима нет.

Ограничения:

- **HEIC.** Фото с камеры iPhone приходит как JPEG. Файл HEIC из галереи Safari обычно
  может конвертировать; поддержка зависит от браузера. Если фото не декодируется,
  покажется просьба сохранить его как JPEG.
- **iOS Safari** не поддерживает `navigator.vibrate`, кнопка «Vibration» на iPhone скрыта;
  звук работает только после нажатия «Start brewing» (требование браузера).
- **Wake Lock** недоступен в старых браузерах и в некоторых режимах энергосбережения.
- Названия кофе, шаги («предсмачивание», «вливание») и оговорки приходят от источника; известные
  слова шагов переводятся, остальное показывается как есть.
- Локальный таймер не управляет машиной; для машины есть отдельный режим (см. «Машина First Brew»).

Проверка на телефонах (эмуляция iPhone 13 и Pixel 5, Playwright):

```sh
POURPOUR_TEST_URL=http://127.0.0.1:8010 node ml/tests/browser-mobile.cjs
```

Сценарии: фото → подтверждение → рецепт, нечитаемое фото → ввод названия, правки признаков,
отмена долгого запроса, языки, поиск → рецепт → таймер, отсутствие горизонтального скролла, главная
кнопка видна без прокрутки на каждом экране, кнопка «назад», размеры кликабельных элементов.
С переменной `POURPOUR_SCREENS_DIR=docs/screens` дополнительно сохраняются скриншоты трёх
экранов и подтверждения в светлой и тёмной теме (375×812); текущие лежат в [docs/screens](../docs/screens).

## Фото и подтверждение

- После OCR всегда карточка «Распознано»: название из каталога или кандидаты,
  страна, обработка, разновидность. Даже точное совпадение требует одного нажатия;
  фокус сразу на «Да, показать рецепт». Редактор вливаний автоматически не открывается.
- Тап по признаку раскрывает его редактирование. Название выбирается тем же поиском
  по каталогу; страна и обработки — из словарей парсера (`GET /api/model`: `countries`,
  `processing`, `varieties`). Несколько обработок можно сохранить одновременно.
- После изменения признака старое совпавшее название снимается, чтобы оно не перекрыло
  правку. Подтверждение отправляет `POST /api/recommend` с полями `Страна: …`,
  `Обработка: …`, `Разновидность: …`. Старый текст OCR в запрос не подмешивается.
- `needs_review` включается при средней уверенности <70 или менее двух слов длиной
  от трёх букв Unicode; цифры и пунктуация не считаются словами. Одиноко прочитанная
  «Колумбия» остаётся полезным признаком, но требует проверки.
- Если OCR ненадёжен и нет страны, обработки и кандидатов, `/api/label` возвращает
  `photo_state: unreadable`, `recipe_data: null`. Экран предлагает переснять или ввести
  название, показывает фото и советы. Общий рецепт — только по явной кнопке,
  через `POST /api/recommend` с пустым текстом. Иначе `photo_state: confirmation`.
- Через 5 секунд распознавания появляется «Это дольше обычного» и «Отмена».
  `AbortController` отменяет ожидание в браузере, поздний ответ не меняет экран.
  Фото остаётся в превью. Уже начатый процесс Tesseract на сервере может завершаться
  до своего лимита 30 секунд; отмена HTTP не прерывает его принудительно.
- Для чужой пачки заголовок состоит из прочитанных признаков, подзаголовок называет
  исходный кофе. Для декафа/эспрессо отдельная оговорка о фильтр-рецептах без декафа;
  распознанная страна не выдаётся за непрочитанную.
- Фото и сырой OCR остаются только в памяти вкладки и временном каталоге OCR.
  Они не попадают в `localStorage`, историю или датасет. В недавние рецепты для
  неизвестного кофе сохраняется название исходного кофе, а не текст с пачки.

Для проверки: сервер `python3 webapp/server.py --port 8010 --machine sim --sim-speed 5`,
затем команда Playwright выше (из корня репозитория). Это эмуляция размеров и ввода
телефонов в браузере, не проверка физической камеры или Safari на реальном iPhone.

## Машина First Brew

Кнопка «Brew on the machine» на экране рецепта появляется, только когда сервер запущен с машиной
и она на связи. Рецепт обжарщика уходит на машину без изменений (доза, вода, температура,
вливания с целевым весом и временем), сервер только проверяет лимиты машины. Экран заваривания
в этом режиме показывает данные с машины: прогрев («Heating water, 72 °C → 96 °C» с прогрессом),
готовность, текущее вливание, вес на весах и температуру; «Pause»/«Resume» и «Stop» отправляют
команды. Обрыв связи показывается явно, с кнопкой «Try again». Локальный таймер остаётся доступен.

Запуск:

```sh
python3 server.py --machine sim               # симулятор, без железа
python3 server.py --machine sim --sim-speed 20 --sim-faults   # быстро и со случайными сбоями
python3 server.py --machine serial            # ESP32 по USB, порт определяется сам
python3 server.py --machine serial:/dev/tty.usbserial-0001
```

По умолчанию `--machine none`: кнопка не показывается, `pyserial` не импортируется.
Для `serial` нужен `pip install -r requirements.txt` (Pillow и pyserial).

API: `GET /api/machine` (подключена ли, состояние, версия прошивки), `POST /api/machine/recipe`
(тело `{"recipe": …}` из `/api/recipes/{id}` или фото-потока), `POST /api/machine/start|pause|resume|abort|tare`,
`GET /api/machine/events` (Server-Sent Events: `state` каждые 250 мс, `link` при подключении и обрыве).
Сервер сам шлёт машине `ping` раз в секунду. Только один сеанс: пока машина в `BREWING`/`PAUSED`,
новый рецепт отвергается (409). Ошибки машины приходят кодом и текстом (`dry_run`, `watchdog`,
`no_temp_sensor`, `overheat`, `limit_*`).

Протокол обмена с платой, состояния и правила безопасности: [docs/PROTOCOL.md](../docs/PROTOCOL.md).
Прошивка: [firmware/README.md](../firmware/README.md). Симулятор (`machine.py`, `SimulatedMachine`)
воспроизводит нагрев, рост веса, долив после выключения помпы, сторожевой таймер и сбои.

Проверка со симулятором: `python3 -m unittest tests.test_machine` и
`node ml/tests/browser-machine.cjs` (сервер с `--machine sim --sim-speed 20`).

## Как получаем рецепт

1. Читаем публичную YML-выгрузку: https://theweldercatherine.ru/bitrix/catalog_export/yandex_848006.php.
2. Выбираем фасовки с `(под фильтр/…)`, объединяем по URL карточки, ищем название локально.
3. В выбранной карточке читаем `#recipe-template[data-id]`. Это ID лота, а не ID фасовки из YML.
4. Читаем публичный API, используемый сайтом: `https://recipes.theweldercatherine.ru/api/v1/recipes?product_id=…&view=true`.
5. Оставляем `device.kind == DRIPPER`, сортируем шаги по `seq_num`. Значения `s`, `1ms`, `2ms` трактуются как 0, 60, 120 секунд, как в скрипте самого источника. Помол отображается в исходном формате `grind_step.grind_sub_step` без самостоятельного пересчёта шкал.

Проверено 15 сентября 2026 на живом каталоге и рецепте «Руанда Суса»: 15 г / 250 г / 98 °C / 2:55, пять вливаний по 50 г.

## API приложения

- `GET /api/search?q=руанда` — результаты, тип совпадения и метаданные источника.
- `GET /api/recipes/{id}` — рецепт выбранного результата поиска.
- `GET /api/health` — состояние локального сервера, без проверки внешнего источника.
- `GET /api/plans`, `GET /api/course`, `GET /api/champions` — тарифы и права, учебный
  контент, рецепты чемпионов (проверенные файлы из `data/`).
- `POST /api/recipes/experiment` — тело `{"recipe": <расчётный рецепт>, "parameter": "grind"|"temperature"|"ratio"}`,
  ответ — два рецепта, отличающиеся ровно одним параметром, и объяснение.

`id` выдаёт наш поиск; произвольные внешние URL API не принимает. Ошибка источника — HTTP 502, неизвестный лот — 404, неверный ввод — 400. Нет рецепта воронки — успешный ответ с пустым `recipes`.

## Кэш и ограничения

Каталог кэшируется на 6 часов, ID карточки — на сутки, рецепты — на час. Кэш хранится в `.cache/` и исключён из Git. При недоступности источника сохранённые данные не старше 7 дней показываются с предупреждением и прежней датой загрузки. Запросы к источнику последовательные, с интервалом минимум 350 мс, тайм-аутом 15 секунд и ограничением ответа 8 МБ. Редиректы запрещены, хосты ограничены двумя доменами источника.

Архив не индексируется. Для некоторых лотов рецепт отсутствует или заполнен частично; приложение показывает это явно. В живом поиске общий рецепт не подставляется. В режиме фото/текста модель предлагает исходный рецепт похожего кофе, страны или общий стартовый рецепт из сохранённой базы; это не проверенная персонализация вкуса.

Сервер стандартной библиотеки предназначен для локального MVP. Публичное развёртывание требует production-сервера/reverse proxy, HTTPS, ограничения частоты запросов и мониторинга источника. Не публиковать этот сервер напрямую в интернет как готовый production-сервис.

## Проверки

```sh
python3 -m unittest discover -s tests -v
```

Тесты работают без сети. Фикстуры — минимальные фрагменты структуры публичных ответов, полученных 15 сентября 2026. Проверяются разделение способов приготовления, порядок шагов, формат времени, неполные данные, поиск, объединение фасовок, ошибки и устаревание кэша.
